発見の速度でパッチ適用: ネットワークOSの全台アップグレードを数か月ではなく数日で

Patching at the speed of discovery: full-fleet Network OS upgrades in days, not months
Cisco Blogs2026-11-20 13:00報道

*AIが脆弱性の発見を加速させる中、Cisco ITはフリート全体のオペレーティングシステム（OS）アップグレード時間を数か月から数日に短縮し、稼働時間を犠牲にすることなく、攻撃者が既知の欠陥を悪用できる期間を縮めた。*

*アップグレードの判断をネットワークインベントリのソース・オブ・トゥルースに統合し、Catalyst Center、Nexus Dashboard、Meraki dashboardの各実装がその判断を実行できるようにしたことで、現在ではCisco ITが管理するデバイスの95%超に対し、提供開始から7日というサービスレベル目標内で、強化されたリリースを適用できている。*

課題：アドバイザリーが是正の速度を上回った

フロンティアAIモデルは、従来の開示とパッチのモデルが吸収できる速度よりも速く脆弱性を発見しており、開示から悪用までの間隔は数週間から数分へと縮まっている。Cisco Product Security Incident Response Team（PSIRT）は、毎月定期的なサイクルでセキュリティ強化リリースを提供し、これらの計画されたリリースについては7日前に通知することで対応した。詳細はRuss Smoak（VP, Information Security）の「Strengthening the Foundation」ブログに記載されている。これらの修正を作り上げるには、Jonathan Felten（Vice President, Engineering）の「Cryptography Rarely Fails Because of the Math」ブログで述べられているように、依然として熟練した人間の判断が必要である。ここでは最終段階、すなわちそれらの展開について扱う。

Cisco ITはお客様と同じハードウェアとソフトウェアを運用しており、従来のワークフローでは各アドバイザリーを個別の調査として扱っていた。私たちは「自分たちは脆弱か？」という一つの問いに答えるためだけに、インベントリのソース・オブ・トゥルース、バックアップ設定、稼働中のデバイス状態の解析に貴重な時間を費やしていた。

私たちの規模では、このやり方は破綻した。

  • 数量と多様性： IOS-XE、IOS-XR、NX-OS、Application Centric Infrastructure（ACI）などを含む60,000台超のデバイスがあり、OSの種類ごとに独自の評価方法が必要だった。
  • バージョンの乱立： アドバイザリーは、重大な問題では3日から7日と短くなり得るサービスレベル目標（SLO）内で是正できる速度よりも速く届いた。各OSの種類は多数のバージョンに細分化されていた。
  • 手作業での実行： デバイスごとのスクリプトと手書きの変更リクエストにより、是正の速度はパッチの提供状況ではなく、エンジニアの空き状況に結び付けられていた。

AIが発見する脆弱性が状況をどう変えるか

強化リリースには多くの修正が含まれ、個々のバグの詳細は記載されないが、それでも展開しなければならない。問いはもはや「自分たちは脆弱か？」ではなく、「どれだけ速く安全にアップグレードできるか？」である。リーダーたちはトレードオフを検討した。アップグレードのための短時間の計画的な中断と、はるかに大きなコストを招き得る計画外のセキュリティ事象との比較である。セキュリティとネットワークのリーダーシップは早い段階で、後者のリスクの方が影響が大きいと合意し、デフォルトでアップグレードすることを決定した。そこで課題は展開へと移った。

私たちのアプローチ：OSイメージ管理の最適化

私たちのアプローチは4つの層にまたがる。判断にはソース・オブ・トゥルースを活用し、Ciscoのコントローラーが実行と検証を行い、プロセスのログはSplunk Cloud Platformに記録され、AIエージェントが隙間を埋める。

人間がゴールデンイメージを設定した後、自動化がアップグレードを実行する：

  • メンテナンスおよび適格性のチェック
  • 変更記録の作成、競合の解決、承認
  • イメージの配布
  • 事前チェック
  • デバイスのアップグレード

これらのステップのいずれかが失敗した場合、そのデバイスのアップグレードは進行しない。

人間の判断は最も重要な部分、すなわちプロセスの監督と、問題が発生した際の解決に残される。各コンポーネントを監督する少数のエンジニアが、数日、あるいは数時間のうちに行われる数千件の変更を監督するまで、効果的にスケールできるようになった。

この戦略の実装を可能にした主要な要件：

  • 正確なソース・オブ・トゥルース： 適切な判断を下すには、信頼できる既知の状態から運用しなければならない。Cisco ITの場合は、構成管理データベース（CMDB）を活用した。CMDBには追加のデバイス属性を伴うインベントリが含まれており、何をアップグレードするか、いつアップグレードするか、どの順序でアップグレードするかを決めるのに使用できるためである。
  • 変更管理： アップグレードは引き続き、すべての変更の追跡や依存関係・競合の特定を含む、確立された変更管理基準に従う。自動化は承認に取って代わるものではない。自動化は、アップグレードが既存の変更プロセスをより一貫して進むのを助ける。標準変更（低リスク、最小限の影響、再現可能）に関する文書化された基準を満たす変更は、変更管理ポリシーで定義された事前承認の経路をたどるため、個別のレビューは不要である。
  • 保証機能： このプロセスは自動化によって動かされるため、ネットワークの状態とアップグレードの進捗を報告することに確信を持てなければならない。自動化は、停止を避けるようアップグレードをスケジュールするために、（単一のソース・オブ・トゥルースで定義された）トポロジーに基づいて判断を下すことができる。アップグレードの進捗はSplunk Cloud Platformに記録され、このデータを使って、デバイスのアップグレードを妨げているコンプライアンス上の問題を特定するダッシュボードを作成している。これにより、チームは障害要因を迅速に解決し、アップグレードを進めることができる。
  • 成功基準の簡素化： アップグレードの成功を測る方法についての考え方を進化させる必要があった。成功は、発生し得る運用上の問題よりも、デバイスが正常にアップグレードされたかどうかに、より重く重み付けされる。運用上の問題が発生した場合は、アップグレードの失敗として扱うのではなく、別個のインシデントとして対処し、必要に応じてエスカレーションする。

これらの判断が下されれば、実行はカスタムプロジェクトではなく、製品の機能になる。お客様がCatalyst Centerで利用できるSoftware Image Management（SWIM）は、組み込みの事前チェック、事後チェック、ロールバックを備え、数千台のデバイスにわたってイメージを配布し有効化する。Nexus DashboardとMeraki dashboardも、それぞれの領域で同様の機能を備えている。

デバイスがまだコントローラーによって管理されていない場合は、自動化とエージェント型オペレーションが隙間を埋める。例えば、Cisco Network ITチームは、AIオペレーションエージェントを活用して、アップグレードバンドルが利用可能になってから3日以内に、Catalyst Centerで管理されていない200台のデバイスをアップグレードした。このAIオペレーションエージェントは、Identity Services Engine（ISE）へのアップグレードの展開も加速させ、日々のネットワーク運用を支援している。

速度を影響範囲に合わせる

アプローチはどこでも同じである。どれだけ速く動くかは、既知の影響によって決まる。

エッジでは、速く進める。 単一のスイッチ、アクセスポイント、あるいは建物の半分をオフラインにすることは、特に営業時間外であれば許容される。トポロジールールにより、もう半分はオンラインに保たれる。事業上重要なチームが24時間体制で稼働している場所では、変更ウィンドウをそれらのチームと直接調整する。それ以外のすべての場所では、アップグレードは自律的に実行される。この戦略を用いることで、30,000台超のデバイスをそれぞれのサービスレベル目標内でアップグレードできた。

データセンターでは、素早く動くが、急ぎはしない。 Application Centric Infrastructure（ACI）ファブリックの各変更はるかに多くのワークロードに影響するため、より慎重でありながらも積極的なアプローチを取る。以前は、1200台のACIファブリックスイッチのアップグレードに6か月かかっていた。現在は5週間であり、5分の1への短縮である。3つの変更が違いを生んだ。

  • より良いコード品質： Cisco engineeringによる高品質なリリースにより、営業時間中でも自信を持ってアップグレードできる。
  • より迅速な承認： 変更リクエストが、ネットワーク構成アイテムへの影響のない変更をより適切に考慮するようになり、承認の遅延の大半が解消された。
  • 自動化： Application Policy Infrastructure Controller（APIC）は、冗長ペアが同時にオフラインにならないよう、スイッチを段階的なグループでアップグレードする。手動チェックに代わる社内の検証が、次のグループが始まる前に、エンドポイント、プロトコルネイバー、インターフェースをアップグレード前のベースラインと比較する。現在では、一度に34台のスイッチのバッチに到達している。
