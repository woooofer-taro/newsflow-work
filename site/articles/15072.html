AI セキュリティ専門家が自律型エージェントのリアルタイムセキュリティを詳述

AI エージェントは、有効な認証情報でログインし、許可されたビジネスアプリケーションにアクセスしたうえで、誰も依頼していない取引を実行しようとすることがある。セキュリティ専門家の Sergey Chubarov によれば、これが自律型エージェントに従来のアイデンティティベースの信頼を適用することの問題であり、アクターを認証することは始まりにすぎない。

Microsoft MVP for Cloud Security、コンサルタント、インストラクター、カンファレンス講演者である Chubarov は、11月12日のセッション「Expert View: Real-Time Security for Autonomous Agents」でこの問題を説明した。このセッションは Zero Trust and Runtime Defense for Agentic AI Summit で行われ、スポンサーの A10 Networks のおかげでオンデマンドリプレイとして公開されている。彼の中心的な推奨事項は、重大な影響を及ぼす行為を、AI エージェントのアイデンティティや一般的な権限だけに基づいてではなく、特定のビジネスタスクに照らして認可することだった。

「そのエージェントが私たちの指示を本当に実行するかどうか、100%確信できるとは限りません……このエージェントが持つすべての権限の使用をただ許可すれば、私たちが想定していなかった操作を実行してしまう可能性があります。」

*Sergey Chubarov、コンサルタント、インストラクター、カンファレンス講演者*

請求書が命令を出し始めるとき

Chubarov のシナリオは、一見ごく普通の依頼から始まった。Supplier A の請求書 1042（$125）をレビューするというものである。エージェントの仕事は請求書を確認してレビューを準備することであり、支払うことではなかった。しかし、その文書には、別の取引を登録し、攻撃者が管理する受取人に $999 を送るようエージェントに指示する悪意ある命令も含まれていた。

これは間接プロンプトインジェクション攻撃である。文書などの信頼度の低い素材に埋め込まれた命令が、エージェントの動作に対して権限を持つかのように扱われる。この攻撃は、エージェントがすでに支払いを開始できる財務システムへのアクセス権を持っている場合に、特に重大な影響を及ぼす。

ライブシミュレーションで、Chubarov は改ざんした請求書を GPT-4o に送信した。モデルは攻撃者への $999 の支払いを提案として返したと、彼は示した。意図的に脆弱にした支払いツールは、認証情報と提案がそのチェックを通過したため、シミュレートされた取引を記録した。実際の資金は移動していない。別の、堅牢化されたツールは、基となるタスクがレビューのみを認可していたため、同じ行為を拒否した。

このデモンストレーションは、すべてのモデルが常に悪意ある文書に従うと主張するものではなかった。Chubarov は、結果はモデルとそのガードレールに依存すると述べ、テストには古いモデルを使用した。彼の主張は、ビジネス上重要な保護策が、モデルが騙されることを拒否することだけに依存してはならないというものだった。

ツールが実行される前にポリシーを適用する

Chubarov は、エージェントが要求する行為と、それを実行する財務 API との間に支払い境界を設けることを提案した。支払い権限を持つエージェントがあらゆる仕事でそれを使ってよいと想定する代わりに、システムは実行時に、呼び出し元、承認されたタスク、行為のパラメータ、および関連するポリシーを評価すべきである。

そのポリシーは、すべての取引を人間のレビュアーに送る必要はない。機密性とビジネスルールに応じて、要求された行為は自動的に許可されるか、拒否されるか、追加承認のために回される。請求書レビューのエージェントは、支払う権限を得ることなく請求書を読めるべきであり、専門エージェントへの引き継ぎが、元のタスクの権限を黙って拡大してはならない。

2つ目のシミュレート攻撃は、別の弱点を示した。サポートエージェントに属する、署名済みで期限切れでないトークンが、そのオーディエンスがサポート API で、スコープがチケットの読み取りであったにもかかわらず、脆弱な財務ツールに受け入れられた。堅牢化されたツールはトークンの意図されたオーディエンスを確認し、支払い要求を拒否した。言い換えれば、トークンの有効性は、特定のリソースを使用する許可と同じではない。

承認は正確な行為と一致しなければならない

人間による承認でさえ、承認された取引が後から変更されうるなら不十分である。Chubarov は、ユーザーが請求書 1042 について Supplier A への $125 を承認する例を示した。3つ目のデモでは、脆弱な経路は既存の承認を見つけたため、受取人や金額の変更を受け入れた。より強力なチェックは、変更された要求がもはや承認された支払いと一致しないため、それを拒否した。

その含意は改ざんにとどまらない。Chubarov は、エージェントタスクのキャンセルは、その保留中の認可済み行為を無効化または停止すべきであり、チェックは支払いが実際に実行される場所で再度実行されるべきだと述べた。エージェントアカウントを無効にするだけでは、すでにキューに入っている支払いが実行されるのを防げない可能性がある。

彼はまた、タイムアウト後の再試行についても警告した。エージェントが支払いに失敗したと報告しても、財務システムはそれでも処理している可能性がある。自動的に再試行すると重複が生じる可能性がある。逆に、エージェントが成功を主張しても、取引が発生した証拠にはならない。結果を決定するのは、エージェントの語りではなく、記録システムでなければならない。

どこから始めるか

リソースが限られている組織に対して、Chubarov は、支払い、返金、権限変更など、重大な影響を及ぼすビジネス上の行為を1つ選び、エージェントがそれをどのように開始できるかをマッピングすることを推奨した。ビジネスオーナーを特定し、許容されるタスクコンテキストと承認条件を指定し、実行時点でチェックを適用し、操作された命令や変更されたパラメータに対してそれらの制御をテストする。

Q&A では、所有者、ライフサイクル、権限の情報を備えたエージェントレジストリを維持することも推奨した。変更できないサードパーティの software-as-a-service API に依存する企業に対しては、より狭い権限を持つエージェント間で職務を分割することを提案した。目的は、レビュー専用のエージェントがそもそも支払い権限を得ることを防ぐことである。

セッションの残り

Chubarov のプレゼンテーションには、脆弱な制御と堅牢化された制御の3つのデモンストレーションがすべて含まれており、さらに、インシデントログ、キューに入った支払い、AI レジストリ、人間による承認、サードパーティ API、共有サービスアカウントに関する Q&A も含まれている。Chubarov はまた、同じ原則を顧客への返金や IT の権限変更に適用することや、エージェントの成功または失敗の報告を受け入れる前に財務システムの受領記録を確認することについても論じた。
