クラウドの過剰支出はツールの不足ではなく説明責任の問題

Cloud overspend is an accountability problem not a tooling gap
Network World2026-11-17 07:00報道

エンタープライズのクラウド問題に対する答えは、より優れたガバナンス、組織構造、可視性、そして説明責任である、とInfotechのNabeel Sherif氏は述べる。

長年クラウドを使用した後、多くの組織は、最初から適切な計画が整っていなかったことに気づき始めている。

Infotechのプリンシパル・アドバイザリー・ディレクターであるNabeel Sherif氏によると、クラウドの採用は設計ではなく緊急性によって推進されることが多かった。それは過去15年間、特にパンデミックの間に加速した。ほとんどの組織はワークロードを移行し、SaaSを採用したが、その作業の背後にある運用モデルは同じペースでは変わらなかった。

インフラストラクチャおよびオペレーションのチームは、ネットワークチームを含め、現在オンプレミスとクラウドを並行して運用しており、多くの場合、それらを統合するモデルはない。彼らは可用性、コスト、リスクに対する責任を負い続けているが、以前に比べて直接的な制御ははるかに少ない。

そのコストは数字に表れている。Sherif氏が引用したFlexeraの2026 State of the Cloud Reportは、IaaSおよびPaaS支出の29%が無駄になっていると推定している。また、組織はパブリッククラウドの予算を平均で17%超過している。

トロントで開催されたInfotech LIVE 2026カンファレンスのセッションで、Sherif氏は、行う必要のある作業を中心にクラウド運用を再設計し、その作業をチームに割り当てるための手法を概説した。

「クラウドはオペレーション作業をなくすわけではない。その性質を変えるだけだ」とSherif氏は述べた。

より多くのツールやトレーニングが問題を外す理由

クラウドの問題に対して多くの組織が示す一般的な反応は、より多くのツールを購入するか、トレーニングを追加することである。しかし、それらの対応が根本的な問題を常に解決するわけではない。

Sherif氏の見方では、データはガバナンス、組織構造、可視性、そして説明責任が進むべき正しい道であることを示している。

クラウドでは所有権と制御がもはや一致しないため、説明責任が行き詰まりの点である。「従来のオペレーションでは、スタックの所有権を引き受けると想定される。クラウドはその前提を壊す」とSherif氏は述べた。「成果については依然としてあなたが責任を負う。しかし、基盤となるすべての仕組みを必ずしも所有しているわけではない。」

彼は、セルフサービスも自動化も問題を解決しないと付け加えた。「再設計がなければ、影響力を伴わない責任を負うことになる」と彼は述べた。「だから、ガバナンス、コスト管理、セキュリティの実践がクラウド以前の考え方に根ざしたままであれば、私たちが導入している制御の仕組みと、私たちが使っている実際の提供の仕組みとの間に緊張が生じることになる。」

作業を中心にクラウド運用を設計する

オペレーションチームは、タスクを直接実行する時間を減らし、サービスの検証、成果の監視、ベンダーの管理により多くの時間を費やすべきである。それは、運用上の影響力が及ぶ必要のある場所を変える。「コスト、信頼性、セキュリティは、デプロイ後ではなく設計によってますます決まるようになっている」とSherif氏は述べた。

Sherif氏の手法は、組織図ではなく作業から始まる。基礎となるステップは、クラウド作業をSaaSの利用、ワークロードのホスティング、カスタムサービスの構築に分類することである。それぞれが異なるスキルと制御を必要とするからだ。

ほとんどの組織はこれらすべての作業を行っているが、同じ割合ではない。Sherif氏は、最もリスクが高い、または作業量が最も多い種類から始めることを勧めている。主にSaaSを利用する組織には、ベンダー管理と統合のスキルが必要である。開発中心の組織には、CI/CDパイプラインと開発者支援の構造が必要である。「ほとんどの組織は3つすべてを同時に行い、それらを同じように扱い、そこでうまくいかなくなる」とSherif氏は述べた。

次のステップは、作業に合った組織構造を選ぶことである。Sherif氏はこれらをパターンと呼ぶ。彼はそれらを、チェックすべき項目としてではなく、組織が組み合わせ、時間とともに変えていく設計上の選択肢として扱っている。

一部のパターンは、統治し学ぶための方法である。クラウドセンター・オブ・エクセレンス（CCoE）とクラウド・コミュニティ・オブ・プラクティスは、あらゆる種類の作業に適用される。その他は、働き方である。DevOps、サイト信頼性エンジニアリング、プラットフォームエンジニアリングは、構築作業にとって最も重要である。「あなたの組織が主にSaaSを利用しているのであれば、それらのパターンのほとんどは優先事項にはならない」とSherif氏は述べた。

その結果は、組織図ではなく、作業領域のフレームワークである。作業領域とは、行う必要のある関連作業のグループである。それは、誰がそれを担当するチームかを誰かが決める前に定義される。

「チームは人と報告構造を含意しており、その議論は、将来行う必要があることではなく、現在誰が何を所有しているかに注意を引きつける」とSherif氏は述べた。

リーダーが始められる場所

Sherif氏は、組織に対し、現在の組織図からではなく作業から始めるよう促した。彼は会場に、自分たちがどのような種類の作業を行っているか、その作業を高品質にするものは何か、そして機能を中心にではなく作業を中心にどのように組織するかを考えるよう求めた。

順序が重要である。「作業を中心に運用モデルを設計し、その後で現在のチームをそれにマッピングして、ギャップと変更点がどこにあるかを特定したい」とSherif氏は述べた。

結果として得られるフレームワークはコミュニケーションツールになる、と彼は述べた。リーダーはそれを使って、自分たちが何を提案し、なぜそうするのかを説明する。スタッフはそれを使って、自分の役割がより広いモデルとどう関係するかを理解する。

彼が最も頻繁に目にする摩擦は、ITを迂回するプロジェクトチームから生じる。チームがベンダーと話をし、ソリューションを構築または購入し、その後になって初めてITに伝える。

期待が揃っていないことがその摩擦を生む。Sherif氏は、赤ちゃんについての友人の言葉を伝えた。「赤ちゃんは愚かなのではなく、ただ新しいだけだ」と彼は述べた。「[もし]人々が物事を知らないなら、その物事について賢くあることを期待することはできない。だから、私たちは期待を設定する必要がある。」
