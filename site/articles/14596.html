ほとんどのチームには、メンテナンスされている道が二つ残っている。Traefik Labs の Traefik Proxy 3.7 はネイティブの Ingress NGINX 互換レイヤーを備えており、F5 NGINX Ingress Controller 5.7 は商用ティアを持つサポート対象製品として NGINX の名を引き継いでいる。第三の選択肢である F5 NGINX Gateway Fabric 2.8 は、従来の Ingress リソースではなく Gateway API を対象としている。2026年11月にこれらから選ぶことは、生の速度よりも、アノテーションの対応範囲、パッチの頻度、ライセンス、そして Gateway API への移行をどれだけ早く計画しているかに関わる。

マネージドクラスター上のチームは、ingress-nginx の退役後に EKS Auto Mode が Gateway API をどう扱うかも読むべきである。クラウドプロバイダーがこの選択の一部をすでに決めつつあるからだ。以下は、メンテナンスされている選択肢の出典付き比較であり、移行パス、価格の実情、そして結論を含む。

2026年11月の Traefik vs NGINX: 実際に何が変わったか

オンラインに残っている「Traefik vs NGINX」ページの多くは、コミュニティの ingress-nginx コントローラーが既定の答えだった世界を描いている。その世界は今年の春に終わった。2026年3月以降も ingress-nginx が積極的にメンテナンスされていると書いているページは古く、新しいクラスターにそれをインストールするよう指示するチュートリアルは、サポートされていないコンポーネントへ誘導している。

この退役は Kubernetes の Ingress API を終わらせたわけではない。Ingress は引き続き利用可能だが、新しいトラフィック管理の作業が Gateway API に着地する一方で、実質的に機能が凍結されている。終わったのは特定の一つのコントローラーである。すでに書いた Ingress オブジェクトは別のコントローラーでも動き続けるため、この区別は重要であり、それはまさに Traefik Labs が売り込んでいる角度である。

「NGINX」と「Traefik」の名のもとにひとまとめにされている四つのものの現状は次のとおり:

  • Traefik Proxy: 活発でオープンソース。現在の機能ラインは 3.7（コードネーム Langres）で、確認されている最新のパッチリリースは v3.7.17。
  • F5 NGINX Ingress Controller: 活発。バージョン 5.7 が 2026年10月14日に発表され、5.7.1 のイメージと Helm チャート 2.8.1 が F5 のドキュメントに記載されている。
  • F5 NGINX Gateway Fabric: 活発。バージョン 2.8 が 2026年10月14日に発表された。NGINX データプレーン上の別個の Gateway API 製品である。
  • コミュニティの ingress-nginx: 2026年3月に退役し、メンテナンスされていない。レガシーとして扱うこと。

F5 の製品と Kubernetes コミュニティのコントローラーは、異なるコードベースと異なるメンテナーを持つため、この退役は F5 のコントローラーには影響しない。人々は両者を絶えず混同しており、その混同こそが、この比較を改めて見直す価値がある主な理由である。

もう一点、時期に関する注記がある。Microsoft は、アプリケーションルーティングアドオンにおけるマネージド NGINX ingress リソースの重要なセキュリティパッチに対する AKS のサポートが 2026年11月に終了すると述べた。クラウドマネージドの ingress も期限が迫っており、AKS を使う組織にとって、これはいつかやるプロジェクトから今四半期のプロジェクトに変わる。

四つの候補と名前が衝突する理由

名前の付け方が問題の半分である。「NGINX」は、Web サーバーおよびリバースプロキシ、退役したコミュニティの Kubernetes コントローラー、F5 のサポート対象 Kubernetes コントローラー、あるいは F5 の新しい Gateway API 実装のいずれをも指しうる。「Traefik」は、オープンソースのプロキシ、またはその上に構築された商用の Traefik Hub プラットフォームのいずれをも指しうる。公平な比較はそれらを分けて扱う。

Traefik Proxy は、オープンソースのリバースプロキシ、ingress コントローラー、ロードバランサーである。Traefik Labs は、35億回を超えるプルと 65,000 を超える GitHub スターを報告しており、Kubernetes、Docker Swarm、AWS を実行するハイブリッドクラウド、マルチクラウド、オンプレミス、ベアメタルの構成での利用を説明している。Traefik Hub は、API 管理、ゲートウェイガバナンス、AI ゲートウェイのための別個の商用レイヤーである。Traefik はプロキシをランタイムのデータプレーン、Hub をガバナンス製品と位置づけており、そのため同社のロードマップの話は今や ingress 以外にも及んでいる。

F5 NGINX Ingress Controller は、オープンソースの NGINX と商用の NGINX Plus の二つの形態で提供される。F5 自身のドキュメントは、商用のインストールオプションには NGINX Ingress Controller のサブスクリプションが必要だと述べている。F5 のドキュメントによれば、この製品には、可動部分を減らしたいチーム向けの、機能が凍結された長期サポート版もあり、リリースから 36 か月間、セキュリティおよび安定性の修正が提供される。

F5 NGINX Gateway Fabric は、NGINX データプレーンで Kubernetes Gateway API を実装する。F5 のドキュメントは 1.x から 2.0 へのアップグレード手順をユーザーに示しており、これは 2.x が現在のメジャーラインであることを示している。これは Ingress Controller のリブランドではなく、F5 は両製品を同じ日、2026年10月14日に現行として発表した。

コミュニティの ingress-nginx は、見分けがつくようにするためだけに比較に含まれる。最後に報告されたリリースは、2026年3月のコントローラー v1.15.1 だった。ある報告によれば SUSE のフォークが独自の修正を出したが、ベンダーのフォークはコミュニティのプロジェクトではなく、独自のサポート条件を持つ。

Gateway API vs Ingress: 本当の分岐点

Traefik vs NGINX の問いは、より大きな問いを隠している。Ingress オブジェクトを書き続けるのか、それとも Gateway API リソースを書き始めるのか。Gateway API の入門ガイドはそのモデルを説明している。GatewayClass、リスナーを所有する Gateway、そしてそれにアタッチされる HTTPRoute などのルートである。Ingress はそのすべてを、一つのオブジェクトとコントローラー固有のアノテーションの山に押し込める。

Gateway API は 2026年2月27日に v1.5 を出荷し、4月21日までに v1.5.1 パッチが出た。その後プロジェクトはリリーストレイン方式を採用し、フリーズ日に準備ができている機能がそのリリースに含まれる。伝えられるところでは、v1.5 は ListenerSet、TLSRoute、HTTPRoute の CORS フィルタリング、クライアント証明書の検証、ReferenceGrant を Standard チャネルに昇格させた。v1.6.0 リリースが 2026年6月30日に続き、v1.7 のリリース候補が 10月16日に報告された。最終タグが付くまでは v1.7 を未リリースとして扱うこと。この API は Kubernetes 本体とは別に出荷されるため、より新しい Gateway API バージョンを採用するのにクラスターのアップグレードは必要ない。

各候補の現状は次のとおり。Traefik Proxy 3.7 は Gateway API v1.5 をサポートしている。F5 は Gateway API ユーザーを NGINX Gateway Fabric に案内しており、そのドキュメントはこれをハイブリッドおよびマルチクラウドの Kubernetes 向けの実装と説明している。これに対し、F5 の Ingress Controller のリリースノートは Ingress 側の機能に焦点を当てており、レビューした資料ではそのGateway API サポートのレベルは確認されていない。Gateway API が移行先であるなら、F5 は二つの製品を運用するか、Gateway Fabric に完全に移行することを想定している。

アップストリームのプロジェクトは Ingress2Gateway という変換ツールも提供しており、Ingress リソースを読み取って Gateway API の同等のものを出力する。コントローラー固有のアノテーションをすべて魔法のように変換するわけではないため、特殊なものは手作業で修正することになる。まず移行先を最初から最後まで見たい場合は、このサイトの Gateway API Kubernetes チュートリアルが、動作する構成を 12 ステップで扱っている。
