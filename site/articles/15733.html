StarlingX 13.0、分散エッジ展開向けにネットワークスタックを更新

StarlingX 13.0 updates the network stack for distributed edge deployments
Network World2026-11-20 07:00報道

StarlingX 13.0 は、サイトルーターが存在しない場合にエッジサーバーがスイッチとして機能できるようにする。

エッジサイトには、データセンターが当然のものとして享受しているネットワーク機器が常に備わっているわけではない。これは、OpenInfra Foundation のオープンソースプロジェクトである StarlingX が、13.0 アップデートで取り組んでいる課題である。

StarlingX は、Linux、Kubernetes、OpenStack、Ceph を組み合わせたオープンソースの分散クラウドプラットフォームである。OpenInfra Foundation がこのプロジェクトをホストしており、Verizon、Vodafone、T-Systems、KDDI などの事業者が 5G や Open Radio Access Network（O-RAN）インフラストラクチャに使用している。今年初め、StarlingX 12.0 アップデートでは、ネットワーキングの時刻同期を保つための高精度タイミング機能が追加された。13.0 アップデートは、それとは異なる一連の課題に取り組む。

主な機能は次のとおり。

  • Gateway API のサポート。 Calico ベースのサポートはホストされるアプリケーションで利用可能であり、プラットフォームサービスは引き続き Ingress NGINX を使用する
  • オプションの認証局。 Enterprise Java Beans Certificate Authority（EJBCA）はプラットフォーム上で動作し、ホストされるアプリケーションに証明書を提供する。
  • サブクラウドの復元。 バックアップは、リモートのエッジサイトであるサブクラウドの、工場出荷時にインストールされたノードに直接復元され、オペレーティングシステムの再インストールは不要である。
  • ダイレクトアップグレード。 オペレーターは、2つ前のリリースから、ホストごとに1回の再起動でアップグレードできる。
  • レイヤー2スイッチング。 新しい Open vSwitch アプリケーションにより、隣にルーターがないサイトのサーバーが、トラフィックをブリッジし、アグリゲーションルーターに直接接続できる。

「OpenvSwitch アプリケーションは、K8S プラットフォームにレイヤー2スイッチングを追加します」と、Wind River の技術スタッフ上級メンバーであり StarlingX Technical Steering Committee のメンバーでもある Greg Waines は *Network World* に語った。「サーバーは、SR-IOV ネットワークインターフェースと他のサーバーとの間でトラフィックをブリッジでき、サイトルーターへトラフィックを転送できます。」

Open vSwitch は、サーバーにサイトルーターが存在しない場所で機能する

Open vSwitch は、OpenStack で長らく有効化されてきた仮想スイッチである。StarlingX 13.0 アップデートでは、これを Kubernetes を通じて管理するオプションのアプリケーションが追加される。

「サーバーの隣にサイトルーターがないエッジおよび通信事業者向けの展開を対象としています」と Waines は述べた。

彼は、Open vSwitch を使うと、2台のサーバーがレイヤー2ネットワーク上でアグリゲーションルーターに直接接続し、互いのバックホールトラフィックと管理トラフィックを運べると説明した。リンクやルーターが故障しても、トラフィックは流れ続ける。

「既存のシステムへの影響はありません」と Waines は述べた。「これはオプションのアプリケーションなので、インストールしない人にとってはプラットフォームの挙動は変わりません。

StarlingX がオプションの認証局を追加

StarlingX 内部への SSL/TLS 認証局（CA）の統合も、新たな機能の一つである。

StarlingX はすでに、証明書の要求と更新を自動化する cert-manager を統合している。しかし、その技術には背後に CA が必要である。「ユーザーには、外部 CA を使うか、証明書への署名のみを行い PKI を提供しない cert-manager 組み込みの発行者を使うという選択肢がありました」と Waines は述べた。

13.0 アップデートには、そのニーズを解決するオプションとして The Enterprise Java Beans Certificate Authority（EJBCA）が含まれる。「EJBCA は、X.509 証明書を発行、管理、失効させる、オープンソースで全機能を備えた認証局（CA）および公開鍵基盤（PKI）です」と Waines は述べた。

EJBCA は、既存のエンタープライズルート配下の下位発行 CA として、または独自の階層のルートとして機能できる。また、証明書プロファイル、ポリシーおよび承認ワークフロー、失効、監査も提供する。このバージョンでは、このアプリケーションはホストされるアプリケーションに証明書を提供する。StarlingX のプラットフォーム証明書は、従来どおり管理される。

Gateway API のサポートはホストされるアプリケーションで利用可能

StarlingX 13.0 はまた、ロードバランサーおよびリバースプロキシとして機能する Kubernetes 内の NGINX Ingress コントローラーに依存している組織向けに、オプションの移行パスを提供する。Kubernetes プロジェクトは、2026年3月にコミュニティ版の NGINX Ingress コントローラーを廃止した。この廃止により、アップストリームのリリース、バグ修正、セキュリティパッチは終了した。既存のデプロイメントは引き続き動作するが、コントローラーはもはや更新を受け取らない。

StarlingX 13.0 には引き続き NGINX ingress が含まれており、Kubernetes v1.35 までをサポートする。これに依存しているユーザーは、このバージョンでは対応する必要がない。Waines は、StarlingX 13.0 が Calico 上に構築された Gateway API のサポートを追加したと指摘した。

「Gateway API は、Ingress の Kubernetes における後継です。インフラストラクチャに関する関心事（Gateway）とアプリケーションのルーティング（HTTPRoute）を分離し、より豊富なルーティングとポリシーをサポートします」と Waines は説明した。「このリリースでは、設定して使用することを選んだホストされるアプリケーションで利用可能であり、ユーザーは今すぐその上に構築を始められます。」

Waines はまた、StarlingX のプラットフォームサービスはまだ Gateway API に移行しておらず、引き続き Ingress NGINX を使用していると指摘した。将来の StarlingX リリースで、プラットフォームサービスを Gateway API に移行し、オペレーター向けの切り替え手順を提供する計画である。

「プラットフォームサービスが移行していないため、このリリースでは既存の Ingress リソースの自動変換はありません」と彼は述べた。「既存の Ingress リソースは引き続き NGINX ingress で動作し、アップグレードによってそれらが変更されることもありません。」

分散クラウドの復旧は、もはや再インストールから始まらない。

このリリースより前は、StarlingX Platform システムをバックアップから復元するには、新規にインストールされた OS が必要だったと Waines は説明した。障害が発生したエッジサイトを復旧するには、まず OS を再インストールしてから復元を実行する必要があった。StarlingX 13.0 はこれを変更し、オペレーターが完全な再インストールなしでサブクラウドを復元できるようにする。

「この機能により、バックアップは、すでにブートストラップされ設定済みの、工場出荷時にインストールされたノードに直接復元でき、再インストールの手順が不要になります」と彼は述べた。

このプロセスは、ハードウェアが交換される故障修理およびディザスタリカバリのケースを対象としている。

「実際には、オペレーターは同一の工場出荷時インストール済みサーバーのプールを保持し、それらを新規デプロイメント（サブクラウドのエンロールメント）と交換用の両方に使用できます」と Waines は述べた。「ハードウェアが故障した場合、オペレーターはプールから交換品を発送し、再インストールなしでそこに復元します。」
