PHP2Shellの余波：さらに18件のPHP欠陥が企業のウェブ管理者に警戒を促す

PHP2Shell aftershock: 18 more PHP flaws put enterprise web admins on alert
Network World2026-11-21 13:00報道

PHP チームは、9.2と評価されたリクエストスマグリングの欠陥を含む複数の脆弱性にパッチを適用した。リスクはサーバー構成に依存し、エンタープライズ環境全体で PHP の棚卸しを行う必要性を改めて示している。

PHP はそのアーキテクチャ内の欠陥を引き続き洗い出しており、今週、PHP2Shell に続いて、さらに多数のセキュリティ問題に対する修正をリリースした。

パッチは18件の脆弱性に対処しており、その中には、認証されていない攻撃者が脆弱なサーバー上でリモートからコードを実行できる可能性のある、重大なリクエストスマグリングの欠陥が含まれる。その他の脆弱性は、PHP のコアエンジン、セッション処理、プロセスマネージャー、そしてウェブサーバーと外部アプリケーションプログラムを橋渡しする Common Gateway Interface（CGI）プロトコルに影響する。

アップデートはサポートされているすべての PHP バージョン向けにリリースされ、PHP 8.5.13、8.4.28、8.3.37、8.2.36 に修正が含まれている。

この開示は、10月に開示された深刻度9.2の一対の脆弱性である PHP2Shell の全面的な影響に、企業が引き続き取り組んでいる中で行われた。これらの欠陥は一部の政府ウェブサイトの完全な閉鎖を招き、一部の推計では、数百万件のエクスプロイト試行の矢面に立たされてきた。

「企業はこのリリースを PHP2Shell の余震として読むべきです。規模は小さいものの、同じ壁を揺さぶります」と、Dickson Research の Frank Dickson 氏は述べた。

RCE、DoS、メモリ破損を可能にする欠陥

今週開示された最も深刻な欠陥の一つである CVE-2026-129289 は、共通脆弱性評価システム（CVSS）で重大の9.2と評価されている。このリクエストスマグリングの脆弱性は、大量アクセスのウェブサイトやアプリのためにコードを実行するバックグラウンドサービスである PHP-FPM に影響する。

悪用された場合、この欠陥により、特定の条件下で PHP-FPM への接続を再利用する脆弱なサーバー上で、認証されていない攻撃者がリモートから PHP コードを実行できる可能性がある。PHP-FPM へのバックエンド接続を再利用する、特定の nginx、Apache、HAProxy、LSAPI の構成に影響する。

コード実行のバグと組み合わされると、「攻撃者をウェブワーカーからサーバー全体へと運ぶ」可能性があると Dickson 氏は説明した。

他のパッチのいくつかも、リモートコード実行（RCE）を可能にし得る脆弱性に対処している。さらに別のものは、情報漏えい、メモリ破損、サービス拒否（DoS）による中断、HTTPS および FTPS URL の安全でない可能性のある処理、クロスサイトスクリプティングなどの問題に対処している。

9.2と評価された CVE-2026-129289 に大きな注目が集まるかもしれないが、より軽微な欠陥も重要だと Dickson 氏は述べた。たとえばあるケースでは、大文字1文字で暗号化が無効になった。HTTPS:// または FTPS:// のように大文字の S で書かれた URL は、リダイレクトを経由しても、パスワード、トークン、フォームデータ、ファイルを、ネットワークを監視している誰にでも平文で送信する可能性がある。

PHP2Shell ほどではないが、それでも高優先度

PHP のコード実行の欠陥を悪用する攻撃者は、PHP ワーカーが触れられるものすべてにアクセスできるようになり、それは「ほぼすべて」だと Dickson 氏は述べた。悪用に成功すると、データベースのパスワード、API キー、クラウドの認証情報、セッションデータを保持する PHP ワーカーの権限でコードが実行される。

たとえば同氏は、「たちの悪い」攻撃経路と呼ぶものを説明した:

  • 脅威アクターはウェブアプリケーションから侵入する。
  • 設定ファイルを読み取る。
  • 顧客データベースをダンプする。
  • 後で戻ってくるためにウェブシェルを仕込む。

同氏は、PHP2Shell がウェブリクエストを処理するすべてのインストールを、ログイン不要でリスクにさらすと PHP が警告したことを指摘した。「このリリースは同じ界隈に戻ってきています。セッションのアップロード進捗、致命的エラーのバックトレース、そして PHP がメモリ不足になったときの挙動です」と同氏は述べた。

Infotech のプリンシパル・サイバーセキュリティ・アドバイザーである Fritz Jean-Louis 氏は、これは PHP2Shell レベルの緊急事態ではないにせよ、高優先度のパッチ適用イベントであることに同意した。重大な脆弱性のいくつかは特定の構成や一般的でない展開シナリオを必要とするものの、「それでも世界で最も広く展開されているウェブランタイムの一つに影響します」と同氏は指摘した。

RCE は、攻撃者にアプリケーションサーバーの制御を与え得るため、最も懸念される結果である。そこから、攻撃者は機密性の高いビジネスデータにアクセスしたり、認証情報やセッショントークンを盗んだり、永続的なバックドアを展開したり、アプリケーションの動作を変更したり、侵害したシステムをより深い侵入の足がかりとして使ったりできる可能性がある。

「情報漏えいやメモリ破損のような、一見それほど深刻でない脆弱性であっても、断固とした攻撃者によって連鎖されると、非常に大きな影響を及ぼし得ます」と Jean-Louis 氏は述べた。

企業が今すべきこと

Dickson 氏は、PHP のバージョン番号だけでは、セキュリティチームが危険にさらされているかどうかは分からないと強調した。バージョン番号の確認は簡単な部分だが、Linux ディストリビューションはバージョン文字列を変えずに修正をバックポートすることが多いため、バージョン番号よりもパッケージの変更履歴の方が多くを物語る。

難しいのはすべてのコピーを見つけることだ。ウェブサーバー、コンテナ、ホスティングコントロールパネル、アプライアンスはいずれも、気づかれないまま PHP を同梱している可能性があると Dickson 氏は述べた。そのうえで、重要な設定を確認する:

  • セッションのアップロード進捗は有効か？
  • PHP 8.5 のワーカーはエラーバックトレースに引数を含めているか？
  • *php-cgi* はインターネットに面しているか？
  • PHP-FPM のステータスページは外部から到達可能か？

同氏はセキュリティチームに対し、インターネットに面した PHP 8.5 サーバー、セッションのアップロード進捗が有効なもの、そして複数のアプリケーションが1つのセッションストアを共有しているあらゆる構成から着手するよう助言した。PHP 8.5 を最初にすべきなのは、新しいバックトレースの欠陥にさらされている唯一のブランチであり、そこでは致命的エラーのバックトレースがデフォルトで有効だからだと同氏は説明した。

「その後、それ以外のすべてを通常の迅速なサイクルでパッチ適用してください」と Dickson 氏は述べた。

同氏は、PHP 8.2 の寿命は残り6週間しかないことを指摘した。2026年12月31日以降はセキュリティ修正を受けられなくなる。つまり、このリリースが受け取る最後の修正の一つになるかもしれない。8.2 を1月まで稼働させ続けるのはリスクの判断である。一方、PHP 8.1 以前は PHP プロジェクトから修正を受けられない。

興味深いことに、新しい PHP 8.5 のバックトレースの欠陥に関する PHP のアドバイザリは、PHP2Shell のリリースである 8.5.12 での変更が、新しい攻撃経路を到達可能にしたと述べている。「緊急の修正は急いで作られ、急ぎの作業は時として新たな脆弱性を生みます」と Dickson 氏は指摘した。

これを踏まえ、同氏の助言は、PHP2Shell のために作成した PHP の棚卸しを保持し、「最新の状態に保つ」ことである。なぜなら、インシデントの最中に「私たちは自社の PHP サーバーをあまりにも多く把握していました」と言った人はいないからだ。

PHP が動作しているあらゆる場所を把握する

Jean-Louis 氏は、セキュリティチームはベンダー製品やアプライアンスに組み込まれたものを含め、すべての PHP 展開を直ちに棚卸しすべきだということに同意した。また、インターネットに面したシステムを優先し、PHP-FPM とセッション管理の構成を検証し、最新のサポート対象 PHP バージョンを「運用上可能な限り迅速に」展開すべきである。

組織はこれを PHP2Shell から学んだ教訓の継続として捉えるべきだと同氏は述べた。ランタイムの脆弱性には、アプリケーションの脆弱性と同じ注意が払われるに値する。PHP2Shell の方が「すぐに悪用可能」で、実際の攻撃をすぐに引き寄せた一方、このリリースは、強固な資産の棚卸し、迅速なパッチ展開、基盤となるソフトウェアコンポーネントの可視性の必要性を改めて示している。

「CISO にとって最大の問題は、PHP を使っているかどうかではありません。それがどこで動いているかをすべて把握しているかどうかです」と Jean-Louis 氏は述べた。
