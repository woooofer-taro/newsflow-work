Microsoft の障害：検出されなかったバグから始まった連鎖的な障害

最初の原因は7月の更新であり、それがなぜか先週まで問題を引き起こさなかった。

先週発生した、Microsoft の多くのサービスにまたがる約1日にわたる世界的な障害を受けて、Microsoft は月曜日に暫定的なインシデント後報告書を公表した。同報告書は問題の複数の原因を特定しており、その中には、問題のある基盤ソフトウェア更新のテストに使用された環境が、実際にそれが稼働するインフラストラクチャと一致していなかったという認識も含まれている。

この報告書の要約は、Microsoft の EVP である Charles Lamanna によってソーシャルメディアに投稿されたもので、障害を連鎖的に引き起こした要因のいくつかを特定していた。

「潜在的な欠陥により、特定の負荷条件下でサーバーが過負荷になり応答しなくなった」と報告書は述べ、「この欠陥は、Microsoft 365 のネットワークゲートウェイサーバー向けに特別に用意された修正の結果であった」と付け加えている。その展開は7月に始まり、報告書によれば「3か月以上にわたり、この変更は影響なく世界中に展開されていた」。

Microsoft は、展開前にこの変更をテストしたものの、そのテスト環境は現実と一致していなかったと認めた。

「通常の負荷テストでは、テストラボで使用されたトラフィックと SKU の構成が異なっていたため、潜在的な問題を検出できなかった」と同社は述べた。「競合の問題は、コア数が多く新しいハードウェアのマシンでより悪化する。一方、当社の負荷テストは、コア数の少ない、より性能の低いハードウェア SKU に重点を置く傾向があった。」

同社の説明によると、無関係な問題によって引き起こされたトラフィックの急増も、この問題を引き起こす一因となり、修正の遅れにもつながった。

「Microsoft 365 内では、分離と高可用性のために設計された、2つの独立した異種のネットワークゲートウェイシステムを維持している」と Microsoft は述べた。「これにより、多くの Microsoft 365 サービスは、障害や中断の際にそれらの間でフェイルオーバーできる。障害の約15時間前に、Teams は代替のネットワークゲートウェイから、Exchange Online も支えているプライマリゲートウェイへフェイルオーバーした。これによりネットワークゲートウェイの負荷が増加し、そのトラフィックパターンが変化した。」

さらに悪いことに、報告書によれば、「前日の無関係な問題により、ネットワークゲートウェイのサーバー容量の約14%が稼働停止になっていた」。Microsoft は、その無関係な問題の詳細を提供しなかった。

これらの要素の組み合わせが障害につながった。

連鎖的な障害

「負荷の増加とサーバー容量の減少により、ネットワークゲートウェイは7月からの潜在的なバグに遭遇した」と Microsoft は述べた。「これにより、サーバーが最終的に応答を停止するまでリクエストが蓄積した。」また、サーバーが接続性を失うと、トラフィック管理システムは自動的にユーザーを他の正常なエンドポイントへルーティングするが、リダイレクトされたトラフィックにより、残りの機能しているエンドポイントで問題が発生する可能性が高まった。

「同じ量の負荷がより少ないサーバーに分散されたため、サーバーからサーバーへと連鎖的な障害が発生した」と報告書は述べた。「2時間足らずで、それまで未知であった欠陥がフリート全体で発生し、サーバーが応答しなくなった。最も少ない時点では、80%以上のサーバーが応答しなかった。」

この連鎖的な一連の問題は、Microsoft が問題の解決を試みる際にも不利に働いた。サーバーがオンラインに戻されるにつれ、待機していたトラフィックの殺到がバグを引き起こし、サーバーが再び応答しなくなったからである。

「通常は自動化されている復旧プロセスは、この広範な応答不能状態からサービスを復元するようには設計されていなかった」と Microsoft は述べた。「さらに、主要なコードの欠陥は数か月前からの潜在的なバグであったため、通常のロールバック、フライティング、機能フラグでは変更を迅速に元に戻すことができなかった。」

なお必要な説明

コンサルタントらは、Microsoft は全体として、システムをサービスに復帰させようとする点で称賛に値する仕事をしたと述べたが、同社はテスト環境がなぜ現実と一致していなかったのかをさらに説明する必要があるとも付け加えた。

「これはビジネスモデルに内在するリスクであり、気の利いた回避策では緩和できないと私は考えている」と、Beauceron Security の CEO である David Shipley は述べた。

「Microsoft は私が思いつく限りのあらゆることを文字どおり行ったが、そのすべてが、見事なまでのエッジケースの形で失敗した。『Microsoft が Microsoft の SKU の複雑さで痛い目に遭う』というのは私のビンゴカードには入っていなかったが、因果応報的な意味では筋が通っている」と彼は述べ、報告書の最も懸念される点は、来週にも Microsoft で同様の連鎖的な一連のエラーが起こらないと信じる具体的な理由を顧客に与えていないことだと強調した。

「これらすべてについて恐ろしいのは、それがどれほど簡単に再び起こり得るかということだ」と Shipley は述べた。「驚くべきは、このエッジケースが起こるまでにこれほど長くかかったことだ。より大きく、より優れたサーバーがこのようなバグの根本原因の一部であったのは、私が思いつく限りこれが初めてだ。」

「潜在的な欠陥がシステム的な障害になる」

Aikido Security のエンタープライズ CISO である Mike Wilkes も同意した。

「皮肉なのは、より新しく強力なハードウェアが実際に障害を増幅させたことであり、スケーラビリティとレジリエンスが同義ではないことを思い出させる」と彼は述べた。「この障害は、エンジニアリング上の前提が本番環境の現実と衝突したときに、潜在的な欠陥がどのようにシステム的な障害になるかを示す教科書的な例だ。Microsoft は、そのテスト環境が自社の本番インフラストラクチャのハードウェア、並行性、トラフィックの特性を表現できていなかったことを、実質的に認めている。」

Wilkes は、報告書のその部分は実に皮肉だと述べた。「最も恥ずべき事実は、Microsoft のステータスページ自体がこの障害によって中断されたことだ」と彼は指摘した。「あなたのインフラストラクチャが壊れていることを伝えるはずのまさにそのシステムが、同じインフラストラクチャの動作に依存しているとは、障害モードについての理解がどれほど情けないものであるべきか。それは単なる技術的な見落としではない。想像力の欠如というアーキテクチャ上の失敗であり、30年以上前に得られているべき経験を適用できなかった失敗だ。」

独立系テクノロジーコンサルタントの Steven Eric Fisher も、テストの食い違いが最大の危険信号だと見ていると述べた。

「テストが本番のハードウェア特性、並行性、トラフィックパターン、運用条件を十分に再現していなければ、重大な欠陥が検出を免れるというリスクを、本質的に受け入れたことになる」と Fisher は述べた。「ここで特に厄介なのは、Microsoft の本番ハードウェアがテスト用ハードウェアより高性能だったにもかかわらず、その追加の能力が欠陥を悪化させたことだ。」

Dickson Research のプリンシパルアナリストである Frank Dickson は、復旧作業のもう一つの問題は、自動化が多くの個別のサーバー障害を静かに処理し、問題を長い間隠していたため、事実上、完全な対応を遅らせたことだと付け加えた。

「火事のずっと前から煙もあった」と彼は指摘した。「Teams のトラフィックは UTC 1:07 AM に共有ゲートウェイへ移り、その後15時間にわたり、一部のリージョンで個別のサーバー障害が現れた。自動化はそれぞれを静かに処理した。優先度の高いアラートが発報されたのは UTC 4:20 PM になってからだった。小さな火を消し続ける自動化は、建物がますます熱くなっているという事実を隠してしまうことがある。」
