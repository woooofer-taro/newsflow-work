攻撃者がOpsShieldの信頼された更新チャネルをサプライチェーン攻撃に変えた

Attackers turned OpsShield’s trusted update channel into a supply-chain attack
Network World2026-11-05 13:00報道

攻撃者は OpsShield の信頼された更新チャネルをサプライチェーン攻撃に変えた

侵害された配布システムにより、脅威アクターは偽の cPGuard アップデートを数千台の Linux サーバーに配信し、そこで root 権限で実行された。

ソフトウェアサプライチェーンの綻びが再び露呈しており、今回は攻撃者が OpsShield の更新プロセスを標的にした。

今週、脅威アクターは侵害した認証情報を使って、悪意のある更新を cPGuard の顧客に配信した。その後、ベンダーのサーバーおよび課金ポータルのアカウントに保存されていたデータにアクセスし、OpsShield のクラウドサーバーを少なくとも3台分コピーした。

同社はアドバイザリーの中で、「把握している攻撃者が到達したすべてのシステムから攻撃者を締め出し、完全には信頼できないシステムは再構築している」と述べている。また、更新版を公開し、顧客に対して cPGuard を最新バージョンに更新し、パスワードを変更し、新しい SSH キーを生成するよう促している。

結局のところ、この無許可アクセスの広がりは、ソフトウェアサプライチェーンが依然として脆弱であること、そしてセキュリティツール自体も脆弱であることを浮き彫りにしている。

「ここでの本当の危険は、攻撃者が信頼されたセキュリティ更新の仕組みを、サーバーに侵入するための経路に変えられたことです」と、Infotech のテクニカルカウンセラーである Erik Avakian 氏は述べた。「サーバーを守るはずのソフトウェアが、サーバーを侵害する発生源になったのです。」

攻撃の詳細

OpsShield はサーバー保護および Web セキュリティソフトウェアを専門としている。同社の cPGuard 製品は、Linux Web ホスティングサーバー向けに設計されたセキュリティスイート、マルウェアスキャナー、ファイアウォールである。

同社は、11月1日から2日の間に、攻撃者が OpsShield の更新配信インフラへの不正アクセスに成功し、約70分間にわたって悪意のある更新を配信したことを公表した。

脅威アクターはまず OpsShield の課金ポータルを探り、偽の身元で顧客アカウントを登録し、無料の cPGuard トライアルを注文した。その後、細工したリクエストを送り、サーバー上でコマンドを実行してデータを収集する能力を得た。盗んだアクセスキーを使って、root（最高レベルの管理者権限）として実行される偽の更新を公開し、機密ファイルをコピーし、OpsShield のクラウドサーバー3台分のコピーを作成した。

OpsShield によると、約2,950台の顧客サーバーが偽の更新を実行し、パスワードハッシュ、root の SSH キー、MySQL の root パスワード、シェル履歴が露出した。攻撃者はまた、顧客の氏名、住所、メールアドレス、ハッシュ化されたパスワードを含む約7,900件の課金ポータルアカウントにもアクセスした。

OpsShield は、アクセスを可能にした正確なリクエストを現在も調査中であり、侵入口の可能性がある2か所にパッチを適用し、関連するベンダーコンポーネントを「1行ずつ」検証したと述べている。攻撃者のアカウントを閉鎖し、盗まれた更新ストレージのキーに加え、「当社アカウント上のすべてのクラウド API トークンとアクセスキー」を失効させた。

同社はまた、攻撃者のセキュアシェル（SSH）を削除し、攻撃者が作成したサーバーのクローンとすべてのスナップショットを削除し、より強力なログイン保護を有効にしてすべての SSH キーとパスワードを置き換え、すべての課金ポータルのログインセッションをリセットしてすべてのキーをローテーションし、課金、ライセンス、社内管理サーバーを、より厳格な PHP とファイアウォールの設定で再構築し始めた。

同社はクリーンな更新も公開した。隠された root シェルを削除する v5.88.26 と、攻撃者が残したスケジュールタスクを削除するフォローアップ版である。さらに、攻撃者がアクセスしたコピーが機能しなくなるよう、cPGuard のライセンスの秘密鍵と公開鍵をすべて再発行し始めた。

同社は管理者に次の対応を勧告した。

  • cPGuard を最新バージョンに更新し、その後 */etc/cron.d/i93677*、*/var/tmp/.i93677/*、*/var/tmp/.cpg91511_sh* が存在しないことを確認する。存在する場合は削除する。
  • サーバー上の root パスワードとすべてのローカルユーザーのパスワードを変更する。
  • 新しい root SSH キーを生成し、それを信頼していたすべてのサーバーから古いキーを削除する。キーが変更されるまで、そのサーバーは侵害されたものとして扱う。
  • MySQL の root パスワードとすべてのデータベースパスワードを変更し、root のシェル履歴に存在するパスワード、API キー、トークンをローテーションする。
  • OpsShield の課金ポータルのパスワードをリセットし、二要素認証を有効にする。
  • 最後に、同社は「攻撃者が手動でお客様のサーバーにログインしたとお伝えした場合は、11月1日より前に取得したクリーンなバックアップからサーバーを再構築してください」と述べた。

OpsShield は透明性を示したが、影響は依然として現実のもの

「率直に言って、これほど率直な侵害の開示を書くベンダーはほとんどありません」と、Dickson Research の Frank Dickson 氏は述べた。「OpsShield はその点で大いに評価されるべきです。」

しかし同氏は、最悪の種類の侵害とは、セキュリティツールによって届けられるものだと指摘した。更新チャネルは意図的に開放されており、セキュリティツールはすべてを見る必要があるため root で動作する。「そのため、偽の更新も root で実行されたのです。」

ホスティングプロバイダーにとって、1台のサーバーに数百の顧客のWebサイトとデータベースが載っていることがある。MySQL の root パスワードはそのすべてを開き、root の SSH キーはそれを信頼する他のすべてのサーバーへのアクセスを与える。シェル履歴にも、入力されたパスワードやトークンが含まれていることが多い。

下流の顧客は、最も知らされないまま最も大きな打撃を受ける可能性があると Dickson 氏は指摘した。ほとんどのWebサイト所有者は、ホスティングプロバイダーがどのセキュリティエージェントを動かしているかを知らないからだ。自動で更新されるすべてのサーバーは、ベンダーのパイプラインを信頼している。

OpsShield は、自らを小規模なチームで、低価格で小規模なホスト向けに販売していると説明しており、それがサプライチェーンの不都合な真実だと Dickson 氏は述べた。「あなたの露出度は、最大のベンダーではなく、あなたのサーバーで root を握る最小のベンダーによって決まります。」

Avakian 氏も、これは企業のソフトウェアサプライチェーンが、その背後にあるシステム、ID、プロセスと同程度にしか安全でないことを思い出させるものだと同意した。「自社のインフラを守るためにできることをすべて行っても、信頼しているサードパーティのサプライヤーを通じて侵害される可能性があります。」

特に懸念されるのは、攻撃者が数千の顧客を一つずつ狙う必要がなく、単一の配信メカニズムを侵害するだけで、ベンダー自身の信頼されたインフラを顧客に向けることができた点だと同氏は指摘した。

サードパーティはリスクを拡大させるが、これは組織がいまだ過小評価している事実だと同氏は述べた。「企業は、サードパーティおよびサプライチェーンのリスク管理にはるかに多くの注意を払う必要があります。」

ゼロトラストは必須

Avakian 氏はまた、盗まれた認証情報がさらなる攻撃の実行に使われうるため、下流の顧客への影響は最初の侵害をはるかに超える可能性があると指摘した。企業は、ソフトウェアサプライヤーと、それらが依存する更新を含めたゼロトラストのアプローチを取るべきである。

「更新が信頼できるソースから来たからといって、安全だと想定できるわけではありません」と同氏は述べた。企業はベンダーリスクをより詳しく調べ、特権認証情報を保護し、ソフトウェアの完全性を検査すべきである。また、更新後の予期しない動作を継続的に監視し、何か問題が起きたときには、迅速にシステムを隔離できるよう備えておくべきである。

「信頼できるサプライヤーでさえ侵害される可能性を前提に計画しなければなりません」と同氏は強調した。「そして、そうしたシナリオを、定期的な机上演習プログラムの一環として訓練する必要があります。」

Dickson 氏は、まず棚卸しから始め、root または管理者権限で動作するすべてのベンダーエージェントを把握することを勧めた。それぞれが更新チャネルだからである。顧客はベンダーに対し、更新の公開キーがどこにあり、それが顧客向けシステムとどのように分離されているかを尋ね、サーバーからのアウトバウンド通信を監視し、シークレットをシェル履歴に残さず、SSH キーを有効期限のある認証情報として扱うべきである。下流の顧客は、ホストに cPGuard を使っているかどうかを直接尋ね、その上で自分自身のパスワードを変更すべきである。

「サーバー上で最も危険なソフトウェアは、自己更新を任せているソフトウェアかもしれません」と同氏は述べた。「それらのベンダーは、root を握っているかのように選んでください。実際に握っているのですから。」
