NGINX HTTP/2のUse-After-Free：CVE-2026-123633

NGINX HTTP/2 Use-After-Free: CVE-2026-123633
Unit 422026-11-27 21:00報道

エグゼクティブサマリー

CVE-2026-123633 は、NGINX HTTP/2 における use-after-free 脆弱性であり、認証されていない攻撃者がサービス拒否を引き起こす可能性がある。CVE レコードにおいて F5 は、アドレス空間配置のランダム化（ASLR）が無効化されているか回避された場合、コード実行が可能になる場合があると述べている。

CVE-2026-123633 は、HTTP/2 クライアント接続を受け付け、空きワーカー接続が少なくなったときにバックエンドへリクエストをプロキシする NGINX サーバーに影響する。断片化されたリクエストにより、アクティブな接続が再利用可能とマークされたままになることがある。接続への負荷がかかっている状況では、NGINX がその接続を閉じ、アクティブなリクエストがまだ使用しているメモリを解放する可能性がある。

F5 の CVE レコードは、この問題を CVSS 4.0 で 9.2 Critical と評価している。NGINX セキュリティアドバイザリのページは、この問題を medium と分類し、バージョン 1.19.7 から 1.30.6、および 1.31.0 から 1.31.8 が影響を受けるとしている。F5 は報告者の一人として memN0ps（Palo Alto Networks Unit 42）を挙げている。

stable ブランチの NGINX 1.30.7 と mainline ブランチの 1.31.9 に修正が含まれている。F5 は影響を受ける NGINX Plus のリリースも掲載している。

管理者は HTTP/2 リバースプロキシの露出を確認し、修正済みの NGINX リリース、または CVE-2026-123633 の修正を含むベンダーパッケージにアップグレードすべきである。

Palo Alto Networks の顧客は、以下の製品およびサービスにより、上記の脅威からより適切に保護される:

組織は、Unit 42 Threat Intel Services とその Deep and Dark Web Service を通じて、個別対応の攻撃者インテリジェンス、アナリストへの直接相談、専門的なエクスポージャー追跡を利用できる。

侵害された可能性がある、または緊急の案件がある場合は、Unit 42 Incident Response チームに連絡すること。

背景

NGINX を調査している際、私は、現在 CVE-2026-123633 として追跡されている HTTP/2 の接続状態の欠陥を独自に発見した。

認証されていないクライアントは、アクティブな接続を再利用可能とマークされたままにする断片化された HTTP/2 リクエストを送信できる。サーバーがリクエスト中にホスト名を解決し、空き接続スロットが少なくなると、NGINX はリクエストの途中でその接続を回収し、その DNS リゾルバーがまだ使用しているメモリを解放する可能性がある。

私は、未変更の NGINX 1.31.7 および 1.31.8 のソースをビルドしたものに対して、AddressSanitizer（ASan）を用いて use-after-free を再現した。NGINX セキュリティアドバイザリのページは、1.19.7 から 1.30.6、および 1.31.0 から 1.31.8 を影響を受けるものとして、1.30.7 と 1.31.9 を修正済みリリースとして掲載している。

私はこの HTTP/2 の use-after-free を F5 に非公開で報告した。F5 の CVE レコードは、これを CVSS 4.0 で 9.2 Critical、CVSS 3.1 で 8.1 High と評価している。NGINX セキュリティアドバイザリのページは、これを Medium と分類している。

Debian ゲスト上での私の ASan テストでは、ASan は解放済みの DNS ルックアップメモリからの最初の読み取りで NGINX を停止させた。

私のテストにおけるリゾルバーの経路は、CVE-2026-123633 として追跡されている HTTP/2 接続のバグに起因する。CVE-2026-123634 は、同じリリースで修正された別個の DNS リゾルバーの脆弱性である。

私はまた、libc ポインターを漏えいさせるメモリ開示の脆弱性も発見した。私はそのアドレスを使って libc のベースを計算し、この開示を CVE-2026-123633 と連鎖させる際に ASLR を回避した。私はこの追加のバグを別の問題として F5 に報告した。攻撃者の VM から、ターゲット VM に対して、root ではない NGINX ワーカーとして認証前のリモートコード実行を達成した。この連鎖にはデフォルトではない NGINX 設定が必要であり、いくつかの試行ではシェルが開かなかった。

F5 はこのメモリ開示を、典型的ではない設定に限定された挙動と評価しており、本稿執筆時点で CVE を割り当てていないため、その詳細とエクスプロイトの手順は省略する。

リゾルバーの Use-After-Free への到達

古くなった再利用可能のマークにより、NGINX は空きスロットが必要になったときにライブな接続を回収できる。私のテストでは、リクエスト時の DNS ルックアップが新しいソケットを開き、ドレインを引き起こした。

私のテストでは、変数 upstream を持つ HTTP/2 プロキシのルートを使用した。この変数は、リテラルの IP アドレスでも設定済みの upstream グループでもないホスト名に評価されたため、NGINX はリクエスト中にそれを検索した。このルックアップでは、新しいリゾルバーの UDP ソケットを開く必要もあった。

ワーカーは、選択されたネームサーバー用のソケットを持っていない場合にのみ、新しい UDP ソケットを開く。キャッシュされた応答や進行中のルックアップも、私がテストしたソケット割り当て時のドレインをスキップする。

DNS ソケットを開くには接続スロットが必要なため、ngx_get_connection() は最初にドレインのチェックを実行する。ngx_drain_connections() は、空きスロットが worker_connections の 16 分の 1 以下になり、かつ再利用可能な接続が少なくとも 1 つ存在する場合に動作する。ドレイン関数はその後、再利用可能キューの末尾からエントリーを選択し、各接続の close フラグを設定して、その read ハンドラーを呼び出す:

私のテストクライアントは、フレームを完了した後、linger をゼロにしてソケットを閉じ、NGINX にはリセットされた接続上のアクティブなリクエストが残された。接続への負荷によってドレインが引き起こされると、HTTP/2 の read ハンドラーはそのソケットで GOAWAY を送信しようとした。

書き込みが成功していればリクエストは実行され続けたはずだが、書き込みは Connection reset by peer で失敗したため、NGINX は接続とリクエストを終了処理した。ASan の解放スタックは ngx_http_upstream_check_broken_connection() を経由する。
