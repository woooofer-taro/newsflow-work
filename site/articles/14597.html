インターネット全体のスキャンで、TCPポート0上に公開されたサービスが見つかった

An internet-wide scan found exposed services on TCP port 0
news.lavx.hu2026-11-07 13:00報道

インターネット全体のスキャンで TCP ポート 0 上の公開サービスが見つかった - news.lavx.hu

セキュリティ研究者の acidvegas は IPv4 に対して TCP ポート 0 をスキャンし、応答したホストの中から、公開された産業用制御機器、警報システム、電話ログを見つけた。この結果は、規格で予約されている番号であっても、ネットワーク機器が転送すればトラフィックを運び得ることを示している。

ポート 0 には、ほとんど交わらない 2 つの役割がある。オペレーティングシステムは、プログラムがネットワークソケットを開くときに、これを利用可能なポートの要求として扱う。一方、ワイヤ上では、TCP ヘッダーは他の 16 ビットの数値と同様にゼロを運ぶことができる。11 月 6 日の報告で、acidvegas は、ポートフォワーディングルールによって IRC ネットワークが TCP ポート 0 上に置かれた経緯を説明し、続いて、これを使う他のサービスのスキャンについて詳述している。

このスキャンでは、プログラマブルロジックコントローラー、警報通信機、業務用電話システムなど、インターネット上の公開されたサーバーやデバイスが見つかった。最も機密性の高い発見は、接続してきた誰にでも通話記録を送信していた 21 台の Avaya IP Office システムに関するものだった。

ソケット API はポート 0 に別の意味を与える

TCP 仕様である RFC 9293 は、送信元ポートと宛先ポートを 16 ビットのフィールドとして定義しており、ゼロを禁止していない。IANA のポートレジストリは、TCP と UDP のポート 0 を予約済みとしている。RFC 6335 は、予約された値はポート範囲の将来の変更のために利用可能なまま残される場合があると説明している。

おなじみの「ポートを選んでほしい」という動作は、ソケット API に由来する。Linux では、ポート 0 で `bind()` を呼び出すプログラムは、カーネルにエフェメラルポートの選択を求める。プログラムが待ち受けを開始するとき、または先にローカルポートをバインドせずに接続するときにも、同じ割り当てが行われ得る。Linux は設定された範囲を `ip(7)` マニュアルに記載している。報告で挙げられているデフォルトの範囲は 32768 から 60999 である。

この動作は、パケットが宛先ポート 0 を運ぶことを妨げない。ただし、一般的なクライアントやサーバーがその番号の使用を拒否することを意味する。acidvegas の報告によると、`nc`、`telnet`、Chromium はそのポートへの接続を拒否し、`socat` と Python の asyncio は接続できた。

Linux カーネルはさらに別の複雑さを生む。その `getpeername()` のパスは、宛先ポートがゼロであることを未接続ソケットの印として扱う。そのため、ポート 0 への TCP 接続が機能している一方で、`getpeername()` が `ENOTCONN` を報告することがある。acidvegas は Python の SSL の失敗をこの不一致にたどり着けた。ブロッキング SSL ラッパーはピアアドレスを確認し、エラーを受け取り、その後 `EAGAIN` を返す読み取りを試みる。Python の asyncio の TLS パスはこの確認を避けるため、動作する。

SYN スキャンでエッジデバイスとサービスが見つかった

acidvegas は masscan を使用した。masscan は、オペレーティングシステムのソケット API に頼らず、独自の TCP パケットを作成する。このスキャンでは、1,173,626 個の IPv4 アドレスから SYN-ACK 応答を受信した。この数は、同数のポート 0 サービスを表すものではなかった。多くのアドレスは、アドレスブロック全体に代わって応答するネットワーク機器の背後にあった。

あるブロック 172.65.0.0/16 は、65,536 アドレスのうち 65,534 で応答した。acidvegas はこのパターンを、何千もの独立したサーバーではなく、ネットワークのエッジでファイアウォールまたはルーターが応答しているものと解釈した。スキャン全体では、1,116,675 個のアドレスがデータを送信せずにハンドシェイクを完了した。バナーを送信した 56,951 個のうち、53,741 個は F5 BIG-IP ロードバランサーからのメッセージを返した。これらの応答と、同じ固定トークンを持つ 305 台のホストを除外した後、acidvegas は他のサービスを持つ 2,905 個のアドレスを分類した。

残りのサービスには、SSH、MySQL と MariaDB、Telnet、HTTP、FTP、VNC、OpenVPN が含まれていた。多くのバナーは組み込み機器を示していた。ルーター、ネットワーク接続ストレージ、デジタルビデオレコーダー、電源コントローラーなどである。単一のプロバイダー内で同じデバイス種別が繰り返されていたことから、一部の顧客はデバイスまたは ISP の設定からポートフォワードルールを引き継いだことが示唆された。acidvegas はこれを確認された原因ではなく、可能性の高い説明として提示した。

一部のウェブインターフェースは、ログインなしで情報を公開していた。ある携帯ルーターは、その WAN および LAN アドレス、無線 MAC アドレス、ネットワーク名、ファームウェアバージョン、稼働時間を返した。ビル自動化コントローラーと HVAC 制御システムも、そのポートでログインページを表示した。

産業用プロトコルがルーターのページと並んで現れた

スキャンは、産業用およびビル制御のプロトコルを話す機器にも到達した。Beckhoff CX5120 組み込み PC は、Windows CE リモートディスプレイのハンドシェイクを送信した。acidvegas はそのバイト列を Beckhoff の CERDISP プロトコルと照合し、挨拶がパスワードなしのセッションを示していることを突き止めた。このプロトコルは画面更新とマウスおよびキーボード入力を運ぶことができ、認証されていない訪問者がコントローラーの画面を見て、操作する経路を得ることになる。

Omron のエンドポイントは、すべての接続が使用中であることを意味する FINS/TCP エラーを返した。FINS を使うと、クライアントは Omron のプログラマブルロジックコントローラーのメモリを読み書きできる。別のホストは、接続が開くとすぐに入力レジスタに対する有効な Modbus リクエストを送信した。これは、監視制御システムが接続してきた相手を誰でもポーリングしているというパターンと一致する。

他のバナーは、電力品質メーター、工場の機械監視ソフトウェア、ホームオートメーションゲートウェイ、警報通信機を示していた。複数の DSC 警報通信機は、デバイス識別子、およびセルラーモデルでは SIM カード番号を含む識別データを送信した。acidvegas は、パケットをオープンソースの DSC-TLink プロジェクトと比較し、そのチェックサムを検証することで、プロトコルを特定した。

これらの発見は、すべてのデバイスが制御を許可していたこと、あるいは攻撃者が公開されたサービスを使用したことを示すものではない。スキャンが、プロトコルとバナーが運用上の詳細を開示するシステムに到達したことを示している。場合によっては、デバイスは、スキャナーが接続を開く以上のリクエストを行う前に情報を送信した。

電話システムは接続時に通話記録を送信した

最も明確なプライバシー上の露出は、21 台の Avaya IP Office 電話システムから生じた。各システムは、acidvegas が接続するとすぐに Station Message Detail Recording データのストリーミングを開始した。記録には、通話時刻、通話時間、電話番号、スタッフ名、内線番号、トランクラベルが含まれていた。

スキャンは各システムから約 7.5 キロバイトを取得し、これは 37 から 62 件の通話に相当する。一部の記録はスキャンの数年前のものであり、他はその数日前のものだった。19 台のシステムは英国のネットワーク上にあり、1 台は米国、1 台は南アフリカにあった。acidvegas は、システムはログの要求なしにそれを送信したと述べた。

そのデータは、サービスを見つけた誰に対しても、従業員の身元や通話パターンを露出させ得る。スキャンの取得上限により、見えている記録は各システムが送信し得るものの一部にすぎなかった。

ポート 0 はサービスを隠さなかった

このスキャンは、通常のツールが避けるのでポート 0 は安全なままだという考えを損なうものである。masscan は接続ベースのスキャナーが飛ばしかねないサービスに到達し、ルーターと転送ルールはトラフィックを宛先まで運んだ。acidvegas の IRC ネットワークは、ファイアウォールルールを使用して、ポート 0 への着信トラフィックをサーバーの通常の平文 IRC ポートにリダイレクトしていた。2 つ目のルールは、ポート 1 をその TLS ポートに転送していた。

ポート番号自体は何の保護も提供しなかった。1 回の SYN スキャンで、公開されたリモートデスクトップ、産業用制御機器、警報システム、データベース、電話ログが見つかった。プロバイダーをまたいで繰り返されたバナーから、acidvegas は誤設定されたポートフォワードを疑ったが、各管理者やデバイスがどのようにしてその設定に至ったかは、スキャンでは確定できなかった。

報告の中心的な教訓は、ソフトウェアの慣習とネットワークの動作との間のギャップから導かれる。クライアントはポート 0 を拒否することがあっても、パケットと転送機器はそこへトラフィックを運び得る。ポートが使用できないという評判に頼る管理者は、データや制御インターフェースを公開するサービスを見逃す可能性がある。
